# Dear Editors — итог системного аудита

Дата: 14 сентября 2026 года.

Этот документ фиксирует инженерный аудит, проведенный после быстрого послойного развития Dear Editors. Это не формальный внешний security audit и не попытка «переписать проект красиво»: целью было найти расхождения в бизнес-логике, опасные обходные пути, мобильные проблемы, N+1, слабые инварианты и ошибки, проявляющиеся при конкурирующих запросах.

## Что проверено и исправлено

### Мобильный редактор и навигация

- Панель форматирования на телефоне возвращена над текстом: она больше не перекрывает правую часть редактора.
- Обычные внутренние переходы больше не открывают новый browsing context, что было особенно неприятно в standalone/PWA-режиме.
- Редактор предупреждает об уходе со страницы с несохраненными изменениями.
- Предпросмотр больше не использует `_blank`, отдельный browsing context, iframe или `srcdoc`: текущая заметка сначала сохраняется как черновик, затем открывается обычным GET в том же приложении и том же окне. Возврат в редактор — обычная ссылка.

### Публикации и доступ к контенту

- Инвариант `status` / `published_at` защищен и в модели, и constraint на уровне БД.
- Будущая запланированная публикация не отдает читателю свое изображение раньше времени по прямому URL.
- Автоматически созданная публикация Вордли больше не редактируется обычным редактором и не принимает generic image upload. Ее источник истины — экран Вордли.
- Обычное редактирование опубликованной заметки не меняет исходное время публикации; оно меняется только при сознательном снятии в черновик и новой публикации.

### Права и destructive flows

- Редакционные мутации закреплены за editor-only путями.
- Отзыв приглашения и MCP-ключа, review/convert письма, Tarot reroll, upload и logout не выполняются через GET.
- Regression tests проверяют обход UI прямыми URL обычным читателем.

### MCP и производительность

- Устранен N+1 при выдаче материалов с `source_letter`.
- Для MCP article/inbox и основных reader/editor экранов установлены query-count/scaling regression baselines.
- Выдача MCP-ключа больше не использует гонку `exists() -> create()`: уникальность решает БД, а конфликт получает ограниченный retry.
- Переход письма `NEW -> REVIEWED` теперь описан в одном сервисе и одинаково используется веб-редактором и MCP.

### Reader activity и Вордли

- Открытие Вордли учитывается одинаково независимо от маршрута входа, без накрутки после каждого игрового POST→redirect→GET.
- Счетчик открытий статьи использует атомарный `F(open_count) + 1` и не держит лишнюю deferred SQLite transaction.
- Одновременные попытки Вордли защищены optimistic compare-and-swap: проигравший запрос перечитывает актуальные `guesses`, а не затирает их старой копией.

### Приглашения и конкурентность

- Accept и revoke приглашения используют conditional UPDATE, поэтому приглашение не может корректно завершить обе конкурирующие операции как одновременно «принятое» и «отозванное».
- Регистрация, проигравшая гонку за уже использованный токен, откатывается вместе с созданным пользователем.

### Изображения и файловое хранилище

- `(article, marker_index)` остается защищен unique constraint.
- Выделение номера изображения через исторический `MAX + 1` обернуто retry-механизмом: collision и кратковременный `SQLITE_BUSY` не превращаются в случайный 500.
- Таро теперь использует тот же общий allocator изображений, что и обычный редактор.
- Самая неприятная находка финального прохода: `post_delete` раньше физически удалял файл сразу, даже если окружающая DB-транзакция затем откатывалась. В результате восстановленная строка могла ссылаться на уже уничтоженный файл. Теперь физическое удаление выполняется только через `transaction.on_commit()`.

## Зафиксированные архитектурные правила

1. `Article.status` и `Article.published_at` образуют один инвариант: draft ↔ `NULL`, published ↔ дата публикации.
2. Вордли владеет своей автоматически созданной публикацией; generic article editor не является вторым источником истины.
3. Таро сохраняет исходную механику ритуала: вопрос + свежий шум, ориентация всей колоды до выборки, выбор из полной колоды, повтор той же карты допустим.
4. MCP может читать редакционные данные и работать с черновиками, но не публикует и не снимает публикации.
5. Файлы удаляются только после успешного commit БД.
6. На SQLite нельзя считать `select_for_update()` реальной блокировкой; критичные операции должны иметь корректное поведение именно на фактическом backend.
7. Предпросмотр — это представление уже сохраненного черновика: POST сохраняет состояние, GET только показывает его. Предпросмотр не имеет отдельной клиентской навигационной механики.

## Что сознательно оставлено

### SQLite

Production сейчас использует SQLite. Для небольшого закрытого издания с низкой интенсивностью записи это приемлемая архитектура, особенно после hardening критичных путей. Но SQLite остается ограничением по write concurrency. Если Dear Editors станет обслуживать несколько активных редакторов/воркеров или заметно больше одновременных записей, правильный следующий шаг — PostgreSQL, а не дальнейшее наращивание SQLite-specific retry.

### Файловое хранилище не является транзакционным

Отложенное удаление решает опасный случай «DB rollback восстановил строку, а файла уже нет». Обратный случай полностью устранить без дополнительной инфраструктуры нельзя: новый файл может успеть записаться на диск, а более поздняя DB-операция — откатиться. Тогда остается orphan-файл, но не битая ссылка в рабочей записи. При необходимости это закрывается периодической reconciliation/cleanup-командой.

### Генерация slug

Slug по-прежнему выбирается как базовое имя + проверка существования + числовой суффикс. Unique constraint не позволит создать два одинаковых slug, но при действительно параллельном создании обычных публикаций один запрос теоретически может получить `IntegrityError`. Для текущего single-editor/SQLite режима риск невысок; при переходе к многопользовательской редакции allocator стоит сделать retry-based.

### Таро и параллельный draw

`draw_date` уникален, поэтому БД не допустит две карты на одну дату. Однако SQLite не дает настоящего row lock через `select_for_update`; экстремальный одновременный draw/reroll все еще может закончиться contention/error вместо красивого проигрыша одного запроса. В текущем ручном редакционном сценарии это низкий риск.

### Мобильный PWA

Кодовые regression tests закрывают найденные ошибки навигации и редактора, но они не заменяют browser-level E2E на конкретном Android/iOS standalone runtime. После крупных изменений мобильный редактор нужно коротко smoke-test'ить на реальном телефоне.

## Итог

После серии audit PR проект больше не выглядит как набор независимо наложенных фич: ключевые состояния имеют явные инварианты, автоматические рубрики знают своего владельца, destructive actions отделены от чтения, MCP и UI меньше дублируют бизнес-правила, а критичные SQLite-конкурентные пути имеют явную стратегию.

На этом системный аудит можно считать завершенным. Дальнейший рефакторинг без конкретной ошибки, измерения или новой бизнес-потребности не нужен: Dear Editors можно снова развивать по фичам, сохраняя текущие regression tests как ограждение от повторного расхождения слоев.
